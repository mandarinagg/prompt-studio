# #60 Jobs (cola, progreso, cancelación) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Exportar (una foto o un lote) sin bloquear el bucle RPC: el trabajo corre en una cola del engine con progreso, cancelación que borra lo parcial y eventos `job.progress|done|failed`. La CLI usa la misma cola. La preview sigue dentro del presupuesto durante un export.

**Architecture:** Un módulo nuevo `pstudio.jobs` con una cola FIFO y **un hilo worker** (libvips ya paraleliza adentro de cada export). Cada job trabaja sobre una **copia** de las fotos y sus pilas tomada al crearlo: el usuario sigue editando y el job no toca `Session.project`. La cancelación es cooperativa: entre fotos con una bandera, y a mitad de una foto con la señal `eval` de libvips (`image.set_kill(True)`), que hace fallar `write_to_file`; `encode` ya escribe a un temporal y lo borra si falla, así que no queda archivo parcial. `asset.export` síncrono (#59) se reemplaza por `job.export`.

**Tech Stack:** Python 3.14 + pyvips 3.2 / libvips 8.18 + Pydantic (engine), React 19 + TS + zustand (app), pytest, vitest.

**Spec:** `docs/superpowers/specs/2026-11-19-m3-app-escritorio-design.md` §5 (Jobs), §6 (RPC: `job.*`, eventos), §8 (preview durante un export), §10 (tests de jobs).

## Mediciones previas (2026-11-23, Ryzen 5 3600, fotos de `tests/fixtures/photos`)
Preview de arrastre 1024 px (`preview.render` por `handle_line`) mientras se exporta `daylight-landscape.jpg` con preset `original`, 6 exports por modo:

| Worker | Export (mediana) | Preview mediana / p95 / p99 | Previews > 100 ms |
|---|---|---|---|
| Sin export | — | 7.5 / — / 11.8 ms | 0 de 2000 |
| Hilo | 3.2–3.4 s | 8.0–8.6 / 26–29 / 37–45 ms | 0–7 de ~1650 |
| Proceso | 4.6 s | 7.9 / 21.7 / 38.9 ms | 12 de 2223 |
| Proceso BELOW_NORMAL | 4.1–5.1 s | 8.0–8.5 / 18–20 / 21–23 ms | 1–10 de ~2400 |
| Proceso en modo segundo plano (CPU + disco bajos) | 5.0–5.3 s | 7.9–8.0 / 21–23 / 38–42 ms | 5–10 de ~2400 |

- El GIL no se traba: un hilo Python que duerme 1 ms nunca esperó más de 50 ms durante el export.
- Los picos de 100–900 ms son **escrituras al disco** del JPEG chico de la preview (`write_bytes`/`os.replace`/`unlink`) mientras el export escribe su archivo grande. Aparecen igual con hilo o proceso, con prioridad baja de CPU y de disco: los causa el sistema de archivos (probablemente el antivirus en tiempo real), no la elección del worker.
- Cancelar con `set_kill` desde la señal `eval`: `write_to_file` falla 15 ms después.
- **Decisión: hilo.** Export ~30 % más rápido, sin costo de arranque, cancela a mitad de foto, comparte la memoria del proceso. Se registra en ADR-0011 con esta tabla. Sacar la preview del disco (bytes por stdio) evitaría los picos que quedan; se anota como seguimiento, no entra en #60.

## Review Focus
1. **Cancelar a mitad de una foto:** no queda ningún archivo en `out_dir` de esa foto (ni el temporal `.<stem>.<hex>.tmp.<ext>`); las fotos ya terminadas del lote **se conservan** y se informan; el hash de todos los originales es igual.
2. **El usuario edita mientras exporta:** el job usa las pilas del momento en que se creó; ni lee ni escribe `Session.project` desde el worker (sin carreras con `commit()`).
3. **El bucle RPC no se bloquea:** `job.export` responde enseguida; durante el job `ping` y `preview.render` responden (test con un export lento real o con un hook que bloquea el worker).
4. **Cierre del engine o del proyecto con un job en curso:** `Session.close()` cancela y espera al worker (con límite) para que no queden temporales; `project.close`/abrir otro proyecto **no** corta el job (escribe en el `out_dir` que se resolvió al crearlo).
5. **Eventos:** orden `job.progress`* → exactamente uno de `job.done` / `job.failed`; el progreso nunca baja y como mucho ~10 eventos por segundo; una foto que falta no hace fallar el lote (queda como error de esa foto en `job.done`).

### Task 1: Engine — cola de jobs y export cancelable

**Files:**
- Create: `engine/src/pstudio/jobs.py`, `engine/tests/test_jobs.py`
- Modify: `engine/src/pstudio/render/io.py` (`encode` acepta `monitor`), `engine/src/pstudio/export.py` (`apply_file` lo pasa), `engine/src/pstudio/project/export.py` (`export_assets` acepta `on_progress` y `cancel`)

**Interfaces (produce):**
- `encode(..., monitor: Callable[[float], bool] | None = None)`: si hay `monitor`, `out.set_progress(True)` y `signal_connect("eval", ...)` con la fracción `progress.percent / 100`; si `monitor` devuelve `False`, `image.set_kill(True)`. El error de libvips por kill se convierte en `Cancelled` (excepción nueva en `pstudio.jobs` o `render.io`; elegir una y documentarla). El temporal se borra como hoy.
- `export_assets(project, ids, out_dir, preset, *, on_progress=None, cancel=None)`: `on_progress(index, total, asset_id, fraction)`; `cancel: threading.Event | None`, chequeado antes de cada foto y desde el monitor. Al cancelar: deja de exportar, devuelve los `Result` ya hechos y marca el resto como cancelado (no como error).
- `pstudio.jobs`:
  - `JobInfo` (Pydantic): `id: str`, `kind: Literal["export"]`, `status: Literal["queued","running","done","failed","cancelled"]`, `total: int`, `done: int`, `current: str | None` (nombre de archivo), `fraction: float` (0–1 del job completo), `out_dir: str`, `results: list[JobItem]`, `error: str | None`, `ms: float | None`. `JobItem`: `asset: str`, `path: str | None`, `error: str | None`.
  - `JobQueue(on_event: Callable[[str, BaseModel], None] | None)`: `submit_export(assets: list[Asset], protected: list[Path], out_dir: Path, preset) -> JobInfo` (copias profundas de los assets), `cancel(job_id) -> JobInfo` (en cola → `cancelled` sin correr; corriendo → bandera; terminado → sin cambios), `list() -> list[JobInfo]` (los últimos 50), `close(timeout=10)` (cancela todo y espera al hilo).
  - Un solo hilo daemon que arranca en el primer `submit`; FIFO.
  - Eventos: `job.progress` (`JobInfo`), `job.done` (`JobInfo` con `status` `done` o `cancelled`), `job.failed` (`JobInfo` con `error`, para excepciones inesperadas, p. ej. no se pudo crear `out_dir`). Progreso limitado a ~10/s salvo el cambio de foto, que siempre se emite.
- [ ] Tests primero (`test_jobs.py`, con fotos generadas en `tmp_path`; una grande, p. ej. 6000×4000 con ruido, para cancelar a mitad):
  - lote de 3 → `job.done` con 3 rutas, progreso no decreciente, `fraction` termina en 1;
  - cancelar a mitad de la 2.ª foto → la 1.ª queda, de la 2.ª no queda nada (ni `*.tmp*`), la 3.ª no se exporta, `status="cancelled"`, hashes de originales iguales;
  - cancelar un job en cola → nunca corre;
  - foto faltante → error en su `JobItem`, el resto se exporta, `status="done"`;
  - `out_dir` imposible → `job.failed`;
  - editar la pila del asset original después de `submit` no cambia lo exportado (snapshot);
  - `close()` con un job corriendo → cancela, el hilo termina, no quedan temporales;
  - `encode` con `monitor` que devuelve `False` → `Cancelled` y sin archivo.
- [ ] Implementar. Verlos pasar. `uv run pytest`, `uv run ruff check . && uv run ruff format --check .`. Commit.
